II. Software Requirement Specification
1. Product Overview 
The J-Tech platform (Web-Based Japanese Practice Support Application for IT Students at FPT University ) is a web-based application developed to eliminate learning barriers, enhance revision efficiency, and consolidate Japanese language competencies aligned directly with the Dekiru Nihongo curriculum. The platform delivers an interactive learning experience by integrating Artificial Intelligence (AI) for pronunciation assessment, personal study path formulation, lesson-aligned practice repositories, and learning motivation powered by gamification mechanics.
The Context Diagram below illustrates the system boundary, along with its interactions and data flows:
Human Actors:
Student SE of FPTU: The central end-users of the system; they log in, complete practice exercises, participate in mock tests, and provide feedback, while receiving learning materials, test results, AI pronunciation evaluations, personalized study paths, and reminder notifications.
Moderator: Manages and contributes curriculum content, practicing materials, and exam question banks; receives lecture content management data.
Admin: Monitors system operational status via the dashboard statistics, approves or rejects account registration requests, and updates user account statuses.
Guest: 
External Integrated Systems & Services:
OAuth (Google Authentication): Receives authentication requests and provides verified user Google account login credentials.
AI Service: Analyzes student practice data and voice audio recordings to evaluate pronunciation and generate personalized learning paths.
Cloudinary: Stores and optimally delivers multimedia learning resources (lecture videos, audios, and images).
Email Service: Automatically dispatches email notifications regarding learning progress reminders.

2.4.1 UCs 01_Login 
Primary Actors
Student, Moderator
, Administrator
Secondary Actors
Authentication Server
Description
Allows users (students, moderators, administrators) to authenticate via an authentication server (Google Account) and access the system based on their assigned roles and account status.
Preconditions
- Users with a valid Google account
- The web browser has accessed the J-Tech system's Login Page.
Normal Flow
1. The user accesses the Login Page and clicks the "Tiếp tục với Google" button.
2. The system sends an authentication request to the Authentication Server (Google OAuth).
3. Google displays the login interface or prompts the user to select a Google account.
4. The user selects an account.
5. The Authentication Server returns authentication details (Google Authentication Information/Token, Email) to the J-Tech system.
6. The J-Tech system checks the account information in the database (User entity):
- Verifies that the account exists in the system.
- Verifies that the account status is "Active."
7. The system initiates a session (issues a JWT) and records the login event (Login Log).
8. The system redirects the user to the Home page.
Alternative Flows
- A1 : At step 6, if the Google account does not yet exist in the system:
+ The system automatically creates a new account record with the default role (Student) and a status of "Pending." . The system redirects the user to the Pending Page, notifying them that the account is awaiting Administrator approval.
+ At Step 6 (Normal Flow), the system detects that the user's Google email already exists in the database with the role `MODERATOR` and status `ACTIVE`, but profile details (such as full name and avatar) are missing:
The system automatically extracts the missing information from the Google account and updates the corresponding User record in the database. The system initializes a session (JWT) with Moderator privileges. The system grants access to Moderator functions without redirecting to the Pending Page. Proceed from Step 8 (Normal Flow).
- A2 : At step 6, if the account status is "Rejected" . The system redirects the user to the Reject page, notifying them that the access request has been denied.
- A3 : At step 6, if the account is locked by the Administrator:  The system denies the login, displays an error message stating that the account is locked or suspended, and prompts the user to contact the Administrator.
- E1: At step 4, the user cancels the operation or closes the Google OAuth popup . The system cancels the authentication process and remains on the Login Page.
- E2 : At step 5, if no response is received or the Google OAuth token is invalid/expired: The system displays At step 5, if no response is received or the Google OAuth token is invalid/expired: The system displays "Xác thực tài khoản Google không thành công. Vui lòng kiểm tra kết nối và thử lại."(MSG19) and provides a "Thử lại" option. 
Postconditions
- Users who successfully log in can access the appropriate permissions and functional screens.
- A session (Session/JWT) is established and recorded in the system logs.
Business rule
 - BR15 : Authentication via Google OAuth: The system exclusively accepts logins using Google accounts; internal registration passwords are not used.
 - BR16 : New student approval: Upon first login, the account is automatically assigned the "Student" role with a "Pending" status; access to learning materials is granted only after Administrator approval.
- BR18 : Permission-based navigation: Upon successful login, the system grants roles access to screens and functions in accordance with the Screen Authorization table.
 - BR01 : User login sessions are managed via JWT. When an account is switched to LOCKED status or logs out, active tokens are immediately invalidated (via Redis Blacklist) and blocked from accessing protected resources.
 - BR12 : Activating pre-created accounts: For Moderator accounts pre-created by the Admin (containing only Email, Role = Moderator, and Status = Active), the user's full name and avatar will be automatically synchronized from Google upon their first login, granting them immediate access to the system without requiring approval.
Triggers
The user clicks the "Tiếp tục với Google" button on the login page.

2.4.2 UCs 02_Sign out
 
Primary Actors
Student , Moderator , Admin
Secondary Actors
None
Description
Allows authenticated users (Students, Moderators, Administrators) to terminate their current active session, invalidate authentication tokens (revoke JWT), and securely log out of the system.
Preconditions
The user has successfully logged into the system and holds a valid, active session (valid JWT token).
Normal Flow
1. The user clicks on their profile avatar or user menu located in the top-right header.
2. The system expands the account dropdown menu (including View Profile, Settings, and Logout).
3. The user selects "Đăng xuất".
4. The system terminates the session:
    - Revokes and invalidates the JWT on the server side (pushes the active token identifier to the Redis Blacklist to prevent replay attacks).
- Clears all stored Access Tokens and Refresh Tokens on the client side (from Local Storage, Session Storage, or HttpOnly Cookies).
5. The system redirects the user to the  Login Page.
Alternative Flows
- E1 (Network Disconnection on Logout): if the network connection fails and the server cannot be reached: The client-side application forcibly purges local session tokens and redirects to the Login Page to safeguard user account credentials.
Postconditions
- The user session is terminated and the JWT is invalidated.
- The user cannot access protected internal resources or use the browser's "Back" button to return to authenticated screens without logging in again.
 
Business rule
- BR-01: User login sessions are managed via JWT. When an account is switched to LOCKED status or logs out, active tokens are immediately invalidated (via Redis Blacklist) and blocked from accessing protected resources.
- BR-116: Once logged out, access to all role-restricted screens is revoked according to the Screen Authorization matrix, requiring fresh re-authentication.
Triggers
The user clicks the "Đăng xuất" button/menu item in the account navigation dropdown.

Normal Flow

6.(If a new image is uploaded) The system uploads the image file to the Cloudinary service and receives the new image URL.
7. The system updates database records with new information and updates fields.
8. The system displays “ Cập nhật hồ sơ thành công”(MSG21), closes the edit form, and shows the latest information on the Profile screen.
Alternative Flows
- A1 :  At step 3 or 4, the user clicks the "Hủy" button or closes the edit form. The system discards all newly entered changes and reverts to displaying the original information on the Profile page.
- E1:  In step 5, if the "Họ và tên" field is
+  Blank the system displays an error message “Nội dung * là bắt buộc không được để trống“ (MSG09)The form retains the entered data, allowing the user to make corrections.
+ Exceeds the specified limit, the system displays an error message “Quá số kí tự quy định vui lòng nhập lại ”(MSG23). The form retains the entered data, allowing the user to make corrections..
- E2 : At step 5, the image file is in an unsupported format (not JPG, PNG, or WEBP) or exceeds the allowed size limit (e.g., < 3MB). The system displays a warning “Ảnh không thuộc định dạng cho phép JPG, PNG, or WEBP hoặc dung lượng lớn hơn 3MB , vui lòng chọn lại (MSG24)”.
- E3 : At step 6, the connection or the image upload process to Cloudinary fails or is interrupted. The system displays an " Lỗi lưu ảnh "(MSG25) notification and does not save the new path to the database.
- E4 : At step 7, writing data to the database fails due to a connection interruption or a system error. The system rolls back, retains the previous state, and displays “Lưu thất bại vui lòng nhập lại”(MSG26).
Postconditions
The user's personal information and profile picture are successfully updated in the database and immediately displayed on the system interface.
Business rule
- BR25 : The email address used for Google OAuth authentication is a fixed identifier; users are not permitted to edit or change this email on the Edit Profile page.
 - BR26 : Fields marked with an asterisk (*) are mandatory; the length must be between 2 and 50 characters.
- BR027 : Uploaded image files must be in an allowed format (PNG, JPG, JPEG, WEBP) and must not exceed the system's maximum file size limit (<3MB).
- BR28 : Users may only edit the profile of the currently logged-in account; they are not permitted to access or modify the profile of another account using this function.
Triggers
The user clicks the "Chỉnh sửa hồ sơ" button in Profile page.

17. The student clicks "Xác nhận".
18. The system performs a soft-delete on the comment record, marks attached files for deletion/cleanup on Cloudinary, removes the comment from the screen, and displays: "Đã xóa thành công!" (MSG02).
Alternative Flows
A01 : Cancellation of delete action:If the student clicks "Hủy bỏ" in the confirmation dialog, the popup closes and the comment remains intact.  
E01 : Blank comment content: If the student clicks "Gửi" with no text, link, or file attached, the system displays an inline error: "Nội dung bình luận không được để trống" (MSG09) and blocks submission.  
E02. Attachment upload failure / Exceeds file size limit: If the attached file exceeds 15 MB or fails during Cloudinary upload, the system highlights the attachment box in red, displays: "Tệp đính kèm không hợp lệ hoặc vượt quá dung lượng cho phép (tối đa 15MB)" (MSG24), and does not save the comment.   
Postconditions
- New or updated classroom posts are persisted in the database and visible on the Classroom Stream.
Business rule
• BR01 (Class Enrollment Requirement): Only students actively enrolled in the classroom associated with the post/assignment have permission to view and post comments.
• BR04 (Author Ownership & Privilege): Students can only edit or delete comments authored by themselves. The class Moderator has overriding administrative permission to delete any inappropriate comment.
• BR08 (Attachment Constraints): Allowed file extensions include PDF, DOCX, ZIP, PNG, and JPG; maximum size is strictly limited to 15 MB per file.
• BR10 (Edit History Audit): Edited comments must permanently display an (Đã chỉnh sửa) indicator with the updated timestamp to preserve audit transparency.
Triggers
The student opens an assignment or class post and interacts with the comment section (submits text, uploads a file, or clicks edit/delete).

Authentication
Token_Refresh_And_Revocation
Background Service / Security Filter
Automatically validates the integrity, claims, and expiration of JWT tokens on every incoming HTTP request. When an account is switched to "Suspended" status by an Administrator, the system immediately revokes the active session and pushes the token identifier to a Redis Blacklist without awaiting natural expiration.

Daily Streak Engine
Daily_Streak_Reset_Job
Scheduled Cron Job
Executes automatically at 00:00:01 (GMT+7) every day. Scans all entries in the User_Streak table; if a student has no qualifying login or completed study activity on the preceding calendar day ($CurrentDate - LastLearningDate > 1$), the system automatically resets the current_streak counter to 0.
3
Study Reminder
Automated_Email_Reminder_Dispatcher
Scheduled Batch Job
Scans students' reminder configuration preferences every 15 minutes. If the scheduled notification time (notification_time) matches and the student has not engaged in any study activity today, the system automatically triggers the Email Service (SMTP/SendGrid) to dispatch a reminder email containing a direct link to continue their streak.
4
SRS Flashcard Algorithm
SRS_Interval_Calculation_Engine
Algorithmic Service (SuperMemo-2 based)
Triggered when a student rates a flashcard ("Remembered" / "Forgot"). Calculates the next optimal review interval (interval_days), updates the ease factor (ease_factor), and computes the next scheduled review date (next_review_date) before persisting the state into the database.
5
AI Speech Processing & Voice Pipeline
AI_Voice_Interactive_Pipeline
Async Worker / Audio Pipeline
Ingests WebM/WAV voice recording streams from the client, normalizes sampling rates (16 kHz), and routes the audio to the STT Engine (Whisper) for Japanese phonetic transcription and alignment. Concurrently handles AI-generated voices (Text-to-Speech) to generate native-sounding conversational prompts, dialogue responses, and audio demonstrations for students.
6
AI Speaking Analysis & Feedback
AI_Kaiwa_Feedback_Processor
AI Integration Service (Google Gemini)
Correlates the student's transcribed speech with the predefined lesson conversational scenario and Dekiru context. Directs Google Gemini to detect grammatical errors, pitch/mora discrepancies, missing long vowels (chōonpu), and double consonants (sokuon), returning structured JSON feedback and correction guidance without assigning numerical test scores.
7
AI Reading Quiz Generator
AI_Reading_Comprehension_Generator
Service Handler / Generative AI
Ingests IT-specialized technical texts, specifications, or scenario scripts uploaded by Moderators. Issues standardized system prompts to Google Gemini to automatically generate 3–5 multiple-choice reading comprehension questions (comprising 4 options, the correct answer, and bilingual Japanese–Vietnamese explanations).
8
Gamification & Ledger Tracking
Coin_EXP_Transaction_Ledger
Transactional Service
Guarantees ACID transactional integrity during reward allocation. Upon exercise/game completion, automatically credits EXP to the user profile, deposits Coins into the digital balance, and commits an immutable entry in Coin_Transaction using an idempotency key to prevent duplicate allocations.
9
Leaderboard Ranking
Leaderboard_Aggregation_Worker
Background Worker (Redis Sorted Sets)
Runs every 10 minutes to aggregate EXP and active streak records across all active students. Refreshes cached rank scores on Redis Sorted Sets to offload real-time relational database queries during concurrent leaderboard access.
10
Media Storage & Cloud Streaming
Cloudinary_Asset_Lifecycle_Manager
Scheduled Maintenance Job
Manages pre-produced AI-generated video lectures uploaded to Cloudinary, ensuring optimal HLS/CDN streaming. Runs weekly on Sundays at 02:00:00 (GMT+7) to reconcile stored media assets with database entity URLs (Lessons, Avatars, Materials), automatically executing Cloudinary Destroy API calls to purge orphaned assets and optimize cloud storage costs.

4. Non-Functional Requirements
4.1 External Interfaces
4.1.1 User Interfaces (UI)
Responsive Web Layout: The web application shall provide a fully responsive layout optimized for desktop and laptop environments (primary resolution:  px; minimum supported resolution:  px).
Japanese Script & Typography Support: The interface must use Unicode Japanese typography (e.g., Noto Sans JP, Hiragino Kaku Gothic Pro) with full cross-browser support for Ruby annotations (<ruby>, <rt>) to render Furigana pronunciation guides seamlessly above Kanji characters without layout breaking.
Integrated Learning Layout: The core learning interface must feature a dual-tab consolidated layout ("Lesson / Lecture Material" tab and "Practice Exercises" tab) to enable instantaneous transitions between theory review and question reinforcement within a single screen.
4.1.2 Hardware Interfaces
Audio Input (Microphone): The system shall interface with standard built-in or external microphone peripherals (via 3.5mm jack, USB, or Bluetooth) supporting a minimum sample rate of 16 kHz for capturing student voice input during AI Speaking sessions.
Audio Output (Speaker/Headphone): The system shall interface with standard audio playback hardware to stream high-clarity pronunciation audio, AI conversational responses, and listening exercises.
4.1.3 Software Interfaces 
Google OAuth 2.0 (Google Identity Services): Interfaced via HTTPS to provide Single Sign-On (SSO) authentication and verify institutional/registered Google user identities.
Cloudinary Media Management Service: Interfaced via secure REST APIs/SDK to store, transform, and deliver multimedia assets. Cloudinary specifically hosts pre-produced, AI-generated lecture videos uploaded by Moderators and delivers them via Adaptive Bitrate Streaming (HLS) and global CDN caching.
Generative AI Service (Google Gemini API): Interfaced via secure HTTPS REST API endpoints to:
Analyze spoken Japanese transcripts for grammar errors and contextual IT communication improvements.
Ingest Moderator-provided technical IT scenarios and automatically generate reading comprehension quizzes (including distractors, correct answers, and bilingual explanations).
Speech-to-Text Engine (OpenAI Whisper API): Interfaced via async HTTPS endpoints to transcribe student voice audio streams into Japanese text with high phonetic accuracy.
AI Voice / Speech Synthesis (Text-to-Speech Engine): Interfaced to generate natural-sounding native Japanese AI voices for spoken prompts, interactive dialogues, and pronunciation benchmarks.
Email Service (SMTP / SendGrid API): Interfaced over TLS (port 587) to automate transactional dispatch of daily study reminders and account status notifications.
4.2 Quality Attributes
4.2.1 Usability 
User Onboarding: A new student shall be able to log in via Google SSO, navigate the curriculum roadmap, and start their first practice session within 3 minutes without external training.
Error Handling & Feedback: All user input validations and runtime exceptions must present clear, polite, and actionable bilingual notifications (referenced via standardized application message codes MSG-xx).
Visual Accessibility: The user interface must adhere to WCAG 2.1 Level AA standards, ensuring high contrast ratios ( for normal text) and accessible UI controls.
4.2.2 Reliability 
System Availability: The platform shall maintain a minimum uptime of 99.5% during operating hours (06:00 to 24:00 GMT+7 daily), excluding scheduled maintenance windows announced at least 24 hours in advance.
Fault Tolerance & Graceful Degradation:
AI Service Unavailability: If third-party AI APIs (Gemini/Whisper) fail or reach quota caps, the system must display an informative banner while allowing uninterrupted access to other core modules (Flashcards, Theory Videos, Mini-tests, Dictation).
Email Service Failure: Notification dispatch failures must be logged and retried automatically up to 3 times via an asynchronous queue without blocking user flows.
Data Integrity & Consistency:
Zero percent ($0\%$) tolerance for data loss regarding test scores, study progress, and digital coin balances.
All reward credits, coin debits, and inventory updates must adhere to strict ACID database transactions with idempotency protection.
Mean Time to Repair (MTTR): In the event of an unplanned system outage, the recovery time shall not exceed 120 minutes.
Database Backup: Automated full database snapshots must be executed daily at 03:00:00 (GMT+7) and retained securely for at least 30 days.
4.2.3 Performance
Page Load & Response Times:
Initial page load (First Contentful Paint - FCP):  seconds on standard broadband connections ( Mbps).
Standard transactional API response time (flashcard flips, quiz submissions, navigation):  milliseconds.
AI Speaking end-to-end latency (Whisper STT processing + Gemini linguistic analysis + AI Voice response):  seconds for an audio input segment up to 15 seconds.
Video Playback Performance: AI-generated lecture videos streamed via Cloudinary CDN must achieve a Time-to-First-Frame (TTFF) of  seconds under normal network conditions.
Concurrency & Throughput: The backend architecture must comfortably support at least 500 concurrent active users without degrading transaction response times by more than $15\%$.
Analytical Dashboard: Administrator dashboard KPIs and charts must render within  seconds using aggregated cache layers (Redis).
4.2.4 Security & Data Privacy 
Role-Based Access Control (RBAC): Strict authorization separation across three user roles: Student, Moderator, and Administrator.
Authentication & Token Lifecycle: User sessions must be managed via cryptographically signed JWT tokens (HMAC-SHA256 or RS256). Access Tokens shall expire in 2 hours; Refresh Tokens shall expire in 7 days. Suspended accounts must have their session tokens instantly invalidated via a Redis token blacklist.
Secrets & Credential Encryption: In accordance with BR-05, all third-party credentials, API keys (Gemini, Cloudinary), and sensitive configuration parameters must be encrypted at rest using AES-256 before database persistence.
Student Voice Privacy: In accordance with BR-42, raw voice audio recordings submitted by students during AI Kaiwa sessions are processed solely within the active session buffer and must be immediately purged thereafter rather than stored indefinitely.
Audit Trail Immutability: In accordance with BR-07, all administrative interventions, account provisioning logs, and critical security events must be recorded into read-only audit log journals (System_Logs) that cannot be modified or deleted via the UI.

5.2 Common Requirements
1. Authentication & Session Management:
All protected routes and API endpoints require a valid JWT Access Token transmitted via the Authorization: Bearer <token> header or HttpOnly cookie.
Access Tokens expire after 2 hours and Refresh Tokens expire after 7 days. If a user's status is changed to LOCKED or REJECTED, the Token_Refresh_And_Revocation filter immediately revokes the session via Redis Blacklist and redirects the user to the Login/Blocked page.
2. Input Validation & Data Sanitization:
All form inputs must be validated on both the client side (React UI) and server side (Spring Boot REST API) before database persistence.
Leading and trailing whitespaces in text inputs (names, titles, search keywords, answers) are automatically trimmed.
All user-generated text (feedback descriptions, classroom posts, comments) must be sanitized to prevent Cross-Site Scripting (XSS) and SQL Injection attacks.
3. Pagination, Search, and Filtering Standards:
All management and history data tables (Student Accounts, Moderator Accounts, Courses, Chapters, Lessons, Question Bank, Feedbacks, Coin Transactions, Audit Logs) support pagination (default 10 or 20 records per page), keyword search, and status filtering.
When a search or filter returns zero records, the system must display a clear empty-state message rather than a blank screen or error page.
4. Multimedia Upload & Streaming Constraints (Cloudinary):
Images (Avatars, Kanji mnemonics, Store items, Feedback screenshots): Allowed formats: JPG, JPEG, PNG, WEBP; maximum size: 3 MB per file.
Classroom Post & Comment Attachments: Allowed formats: PDF, DOCX, ZIP, PNG, JPG, MP3; maximum size: 15 MB per file.
Lecture & Listening Videos / Audio: Stored on Cloudinary and delivered via HTTPS/HLS adaptive streaming URLs (video_url, audio_url) along with public_id for lifecycle management.
5. Date, Time, and Localization Standards:
The user interface is presented in Vietnamese combined with Japanese learning content (Kanji, Hiragana, Katakana, Furigana Ruby tags <ruby><rt>).
All timestamps, daily study reminder schedules, and login/study streak evaluations operate on the Asia/Ho_Chi_Minh (GMT+7) timezone and are formatted as DD/MM/YYYY or DD/MM/YYYY HH:mm on the UI.
6. Soft Deletion & Historical Data Integrity:
Any master record (course, chapter, lesson, grammar, vocabulary, kanji, conjugation_form, question, test, store_item, user_account) that is referenced by student learning progress, test attempts, or coin transactions must never be physically deleted (HARD DELETE); the system must transition its status to ARCHIVED, INACTIVE, or HIDDEN.
