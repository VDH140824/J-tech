II. Software Requirement Specification
1. Product Overview 
The J-Tech platform (Web-Based Japanese Practice Support Application for IT Students at FPT University ) is a web-based application developed to eliminate learning barriers, enhance revision efficiency, and consolidate Japanese language competencies aligned directly with the Dekiru Nihongo curriculum. The platform delivers an interactive learning experience by integrating Artificial Intelligence (AI) for pronunciation assessment, personal study path formulation, lesson-aligned practice repositories, and learning motivation powered by gamification mechanics.
The Context Diagram below illustrates the system boundary, along with its interactions and data flows:
Human Actors:
Student SE of FPTU: The central end-users of the system; they log in, complete practice exercises, participate in mock tests, and provide feedback, while receiving learning materials, test results, AI pronunciation evaluations, personalized study paths, and reminder notifications.
Moderator: Manages and contributes curriculum content, practicing materials, and exam question banks; receives lecture content management data.
Admin: Monitors system operational status via the dashboard statistics, approves or rejects account registration requests, and updates user account statuses.
Guest: 
External Integrated Systems & Services:
OAuth (Google Authentication): Receives authentication requests and provides verified user Google account login credentials.
AI Service: Analyzes student practice data and voice audio recordings to evaluate pronunciation and generate personalized learning paths.
Cloudinary: Stores and optimally delivers multimedia learning resources (lecture videos, audios, and images).
Email Service: Automatically dispatches email notifications regarding learning progress reminders.

2.4.1 UCs 01_Login 
Primary Actors | Student, Moderator, Administrator | Secondary Actors | Authentication Server
Description | Allows users (students, moderators, administrators) to authenticate via an authentication server (Google Account) and access the system based on their assigned roles and account status.
Preconditions | - Users with a valid Google account- The web browser has accessed the J-Tech system's Login Page.
Normal Flow | 1. The user accesses the Login Page and clicks the "Tiếp tục với Google" button.2. The system sends an authentication request to the Authentication Server (Google OAuth).3. Google displays the login interface or prompts the user to select a Google account.4. The user selects an account.5. The Authentication Server returns authentication details (Google Authentication Information/Token, Email) to the J-Tech system.6. The J-Tech system checks the account information in the database (User entity):- Verifies that the account exists in the system.- Verifies that the account status is "Active."7. The system initiates a session (issues a JWT) and records the login event (Login Log).8. The system redirects the user to the Home page.
Alternative Flows | - A1 : At step 6, if the Google account does not yet exist in the system:+ The system automatically creates a new account record with the default role (Student) and a status of "Pending." . The system redirects the user to the Pending Page, notifying them that the account is awaiting Administrator approval.+ At Step 6 (Normal Flow), the system detects that the user's Google email already exists in the database with the role `MODERATOR` and status `ACTIVE`, but profile details (such as full name and avatar) are missing:The system automatically extracts the missing information from the Google account and updates the corresponding User record in the database. The system initializes a session (JWT) with Moderator privileges. The system grants access to Moderator functions without redirecting to the Pending Page. Proceed from Step 8 (Normal Flow).- A2 : At step 6, if the account status is "Rejected" . The system redirects the user to the Reject page, notifying them that the access request has been denied.- A3 : At step 6, if the account is locked by the Administrator:  The system denies the login, displays an error message stating that the account is locked or suspended, and prompts the user to contact the Administrator.- E1: At step 4, the user cancels the operation or closes the Google OAuth popup . The system cancels the authentication process and remains on the Login Page.- E2 : At step 5, if no response is received or the Google OAuth token is invalid/expired: The system displays At step 5, if no response is received or the Google OAuth token is invalid/expired: The system displays "Xác thực tài khoản Google không thành công. Vui lòng kiểm tra kết nối và thử lại."(MSG19) and provides a "Thử lại" option. 
Postconditions | - Users who successfully log in can access the appropriate permissions and functional screens.- A session (Session/JWT) is established and recorded in the system logs.
Business rule |  - BR09 : Authentication via Google OAuth: The system exclusively accepts logins using Google accounts; internal registration passwords are not used. - BR10 : New student approval: Upon first login, the account is automatically assigned the "Student" role with a "Pending" status; access to learning materials is granted only after Administrator approval.- BR11 : Permission-based navigation: Upon successful login, the system grants roles access to screens and functions in accordance with the Screen Authorization table. - BR01 : Session control and account locking: Login sessions are managed via JWT; accounts with a "Suspended" status have their sessions immediately invalidated and are blocked from logging in. - BR12 : Activating pre-created accounts: For Moderator accounts pre-created by the Admin (containing only Email, Role = Moderator, and Status = Active), the user's full name and avatar will be automatically synchronized from Google upon their first login, granting them immediate access to the system without requiring approval.
Triggers | The user clicks the "Tiếp tục với Google" button on the login page.

2.4.2 UCs 02_Sign out
 
Primary Actors | Student , Moderator , Admin | Secondary Actors | None
Description | Allows authenticated users (Students, Moderators, Administrators) to terminate their current active session, invalidate authentication tokens (revoke JWT), and securely log out of the system.
Preconditions | The user has successfully logged into the system and holds a valid, active session (valid JWT token).
Normal Flow | 1. The user clicks on their profile avatar or user menu located in the top-right header.2. The system expands the account dropdown menu (including View Profile, Settings, and Logout).3. The user selects "Đăng xuất".4. The system terminates the session:    - Revokes and invalidates the JWT on the server side (pushes the active token identifier to the Redis Blacklist to prevent replay attacks).- Clears all stored Access Tokens and Refresh Tokens on the client side (from Local Storage, Session Storage, or HttpOnly Cookies).5. The system redirects the user to the  Login Page.
Alternative Flows | - E1 (Network Disconnection on Logout): At step 6, if the network connection fails and the server cannot be reached: The client-side application forcibly purges local session tokens and redirects to the Login Page to safeguard user account credentials.
Postconditions | - The user session is terminated and the JWT is invalidated.- The user cannot access protected internal resources or use the browser's "Back" button to return to authenticated screens without logging in again. 
Business rule | - BR-01: User sessions are managed via JWT; upon logout, active tokens are immediately invalidated to prevent unauthorized reuse.- BR-11: Once logged out, access to all role-restricted screens is revoked according to the Screen Authorization matrix, requiring fresh re-authentication.
Triggers | The user clicks the "Đăng xuất" button/menu item in the account navigation dropdown.

2.4.5 UCs 05_View notifications
Primary Actors | Student, Moderator, Administrator | Secondary Actors | None 
Description | Allows authenticated users (Students, Moderators, Administrators) to view a list of in-app notifications (such as account approval decisions, feedback resolution updates, coin reward credits, and study reminders) and mark individual or all notifications as read. 
Preconditions | The user has successfully logged into the system with an active account 
Normal Flow | 1. The user clicks on the notification bell icon located in the top-right navigation header.2. The system identifies the authenticated user (User Id) from the active session and queries the Notification table for records belonging to that user, ordered by creation timestamp descending (Created At DESC).3. The system renders the notification dropdown panel/list, displaying the following details for each item:    - Notification title (Title) and summary message (Content).    - Notification category (Notification Type: Account Approval, Feedback Resolution, Coin Reward) and timestamp .    - Read status indicator (Is Read: unread notifications are visually highlighted with a dot indicator or bold text).4. The user clicks on a specific unread notification (Is Read = false).5. The system updates the notification's status to read (Is Read = true), records the read timestamp (Read At = CURRENT_TIMESTAMP) in the database, and decrements the unread notification badge counter on the bell icon6. The system displays the full notification content or redirects the user to the corresponding functional screen associated with the notification.
Alternative Flows | - A1 (Mark All as Read): At step 3, the user clicks the "Đánh dấu tất cả đã đọc” button: The system batch-updates all unread notifications (Is Read = false) for the current user to Is Read = true, sets Read At = CURRENT_TIMESTAMP, and clears the unread badge counter on the header bell icon.- A2 (Filter Unread Notifications): At step 3, the user selects the "Chưa đọc” filter tab: The system filters and displays only notification entries where Is Read = false.- E1 (Data Retrieval / Server Error): At step 2 or step 5, if a database connection error or server exception occurs: The system displays an error banner: "Không tải được dữ liệu , hãy thử lại sau" (MSG20) and provides a "Thử lại" button.
Postconditions | - The user's notification list is accurately displayed on the interface.- The read status (Is Read = true) and read timestamp (Read At) of selected notifications are persisted in the Notification table in the database.
Business rule | - BR89 : Users are strictly authorized to view and mark as read only the notifications dispatched to their own account 
Triggers | The user clicks on the notification bell icon in the top navigation bar.

4. Non-Functional Requirements
4.1 External Interfaces
4.1.1 User Interfaces (UI)
Responsive Web Layout: The web application shall provide a fully responsive layout optimized for desktop and laptop environments (primary resolution:  px; minimum supported resolution:  px).
Japanese Script & Typography Support: The interface must use Unicode Japanese typography (e.g., Noto Sans JP, Hiragino Kaku Gothic Pro) with full cross-browser support for Ruby annotations (<ruby>, <rt>) to render Furigana pronunciation guides seamlessly above Kanji characters without layout breaking.
Integrated Learning Layout: The core learning interface must feature a dual-tab consolidated layout ("Lesson / Lecture Material" tab and "Practice Exercises" tab) to enable instantaneous transitions between theory review and question reinforcement within a single screen.
4.1.2 Hardware Interfaces
Audio Input (Microphone): The system shall interface with standard built-in or external microphone peripherals (via 3.5mm jack, USB, or Bluetooth) supporting a minimum sample rate of 16 kHz for capturing student voice input during AI Speaking sessions.
Audio Output (Speaker/Headphone): The system shall interface with standard audio playback hardware to stream high-clarity pronunciation audio, AI conversational responses, and listening exercises.
4.1.3 Software Interfaces 
Google OAuth 2.0 (Google Identity Services): Interfaced via HTTPS to provide Single Sign-On (SSO) authentication and verify institutional/registered Google user identities.
Cloudinary Media Management Service: Interfaced via secure REST APIs/SDK to store, transform, and deliver multimedia assets. Cloudinary specifically hosts pre-produced, AI-generated lecture videos uploaded by Moderators and delivers them via Adaptive Bitrate Streaming (HLS) and global CDN caching.
Generative AI Service (Google Gemini API): Interfaced via secure HTTPS REST API endpoints to:
Analyze spoken Japanese transcripts for grammar errors and contextual IT communication improvements.
Ingest Moderator-provided technical IT scenarios and automatically generate reading comprehension quizzes (including distractors, correct answers, and bilingual explanations).
Speech-to-Text Engine (OpenAI Whisper API): Interfaced via async HTTPS endpoints to transcribe student voice audio streams into Japanese text with high phonetic accuracy.
AI Voice / Speech Synthesis (Text-to-Speech Engine): Interfaced to generate natural-sounding native Japanese AI voices for spoken prompts, interactive dialogues, and pronunciation benchmarks.
Email Service (SMTP / SendGrid API): Interfaced over TLS (port 587) to automate transactional dispatch of daily study reminders and account status notifications.
4.2 Quality Attributes
4.2.1 Usability 
User Onboarding: A new student shall be able to log in via Google SSO, navigate the curriculum roadmap, and start their first practice session within 3 minutes without external training.
Error Handling & Feedback: All user input validations and runtime exceptions must present clear, polite, and actionable bilingual notifications (referenced via standardized application message codes MSG-xx).
Visual Accessibility: The user interface must adhere to WCAG 2.1 Level AA standards, ensuring high contrast ratios ( for normal text) and accessible UI controls.
4.2.2 Reliability 
System Availability: The platform shall maintain a minimum uptime of 99.5% during operating hours (06:00 to 24:00 GMT+7 daily), excluding scheduled maintenance windows announced at least 24 hours in advance.
Fault Tolerance & Graceful Degradation:
AI Service Unavailability: If third-party AI APIs (Gemini/Whisper) fail or reach quota caps, the system must display an informative banner while allowing uninterrupted access to other core modules (Flashcards, Theory Videos, Mini-tests, Dictation).
Email Service Failure: Notification dispatch failures must be logged and retried automatically up to 3 times via an asynchronous queue without blocking user flows.
Data Integrity & Consistency:
Zero percent ($0\%$) tolerance for data loss regarding test scores, study progress, and digital coin balances.
All reward credits, coin debits, and inventory updates must adhere to strict ACID database transactions with idempotency protection.
Mean Time to Repair (MTTR): In the event of an unplanned system outage, the recovery time shall not exceed 120 minutes.
Database Backup: Automated full database snapshots must be executed daily at 03:00:00 (GMT+7) and retained securely for at least 30 days.
4.2.3 Performance
Page Load & Response Times:
Initial page load (First Contentful Paint - FCP):  seconds on standard broadband connections ( Mbps).
Standard transactional API response time (flashcard flips, quiz submissions, navigation):  milliseconds.
AI Speaking end-to-end latency (Whisper STT processing + Gemini linguistic analysis + AI Voice response):  seconds for an audio input segment up to 15 seconds.
Video Playback Performance: AI-generated lecture videos streamed via Cloudinary CDN must achieve a Time-to-First-Frame (TTFF) of  seconds under normal network conditions.
Concurrency & Throughput: The backend architecture must comfortably support at least 500 concurrent active users without degrading transaction response times by more than $15\%$.
Analytical Dashboard: Administrator dashboard KPIs and charts must render within  seconds using aggregated cache layers (Redis).
4.2.4 Security & Data Privacy 
Role-Based Access Control (RBAC): Strict authorization separation across three user roles: Student, Moderator, and Administrator.
Authentication & Token Lifecycle: User sessions must be managed via cryptographically signed JWT tokens (HMAC-SHA256 or RS256). Access Tokens shall expire in 2 hours; Refresh Tokens shall expire in 7 days. Suspended accounts must have their session tokens instantly invalidated via a Redis token blacklist.
Secrets & Credential Encryption: In accordance with BR-05, all third-party credentials, API keys (Gemini, Cloudinary), and sensitive configuration parameters must be encrypted at rest using AES-256 before database persistence.
Student Voice Privacy: In accordance with BR-42, raw voice audio recordings submitted by students during AI Kaiwa sessions are processed solely within the active session buffer and must be immediately purged thereafter rather than stored indefinitely.
Audit Trail Immutability: In accordance with BR-07, all administrative interventions, account provisioning logs, and critical security events must be recorded into read-only audit log journals (System_Logs) that cannot be modified or deleted via the UI.

5.2 Common Requirements
1. Authentication & Session Management:
All protected routes and API endpoints require a valid JWT Access Token transmitted via the Authorization: Bearer <token> header or HttpOnly cookie.
Access Tokens expire after 2 hours and Refresh Tokens expire after 7 days. If a user's status is changed to LOCKED or REJECTED, the Token_Refresh_And_Revocation filter immediately revokes the session via Redis Blacklist and redirects the user to the Login/Blocked page.
2. Input Validation & Data Sanitization:
All form inputs must be validated on both the client side (React UI) and server side (Spring Boot REST API) before database persistence.
Leading and trailing whitespaces in text inputs (names, titles, search keywords, answers) are automatically trimmed.
All user-generated text (feedback descriptions, classroom posts, comments) must be sanitized to prevent Cross-Site Scripting (XSS) and SQL Injection attacks.
3. Pagination, Search, and Filtering Standards:
All management and history data tables (Student Accounts, Moderator Accounts, Courses, Chapters, Lessons, Question Bank, Feedbacks, Coin Transactions, Audit Logs) support pagination (default 10 or 20 records per page), keyword search, and status filtering.
When a search or filter returns zero records, the system must display a clear empty-state message rather than a blank screen or error page.
4. Multimedia Upload & Streaming Constraints (Cloudinary):
Images (Avatars, Kanji mnemonics, Store items, Feedback screenshots): Allowed formats: JPG, JPEG, PNG, WEBP; maximum size: 3 MB per file.
Classroom Post & Comment Attachments: Allowed formats: PDF, DOCX, ZIP, PNG, JPG, MP3; maximum size: 15 MB per file.
Lecture & Listening Videos / Audio: Stored on Cloudinary and delivered via HTTPS/HLS adaptive streaming URLs (video_url, audio_url) along with public_id for lifecycle management.
5. Date, Time, and Localization Standards:
The user interface is presented in Vietnamese combined with Japanese learning content (Kanji, Hiragana, Katakana, Furigana Ruby tags <ruby><rt>).
All timestamps, daily study reminder schedules, and login/study streak evaluations operate on the Asia/Ho_Chi_Minh (GMT+7) timezone and are formatted as DD/MM/YYYY or DD/MM/YYYY HH:mm on the UI.
6. Soft Deletion & Historical Data Integrity:
Any master record (course, chapter, lesson, grammar, vocabulary, kanji, conjugation_form, question, test, store_item, user_account) that is referenced by student learning progress, test attempts, or coin transactions must never be physically deleted (HARD DELETE); the system must transition its status to ARCHIVED, INACTIVE, or HIDDEN.
